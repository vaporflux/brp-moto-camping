# BRP Trip Planner — Build Spec

**For:** Claude Code, picking this project up cold.
**Owner:** Robert Mitchell. Rides a BMW R1250GSA. Planning a multi-day Blue Ridge Parkway trip with friends.
**Prepared:** August 18, 2026.

---

## 1. What exists today

A working, deployed static map: `v1/index.html`. Self-contained, Leaflet embedded, ~270 KB. It plots 32 shower-equipped campgrounds along the Parkway (MP 0–469) with filters and detail cards, plus the current road closures drawn on the Parkway centerline. It's live on Vercel from a GitHub repo.

**This spec is about v2.** v1 is a reference implementation and a data source, not something to preserve. Feel free to rebuild the UI entirely.

## 2. What v2 needs to do

Turn the map from a *lookup tool* into a *trip planner*:

1. **Pick a start point and an end point** (a town, an address, or a Parkway milepost).
2. **Add stops in order** — campgrounds from the existing dataset, fuel stops from the new one, plus arbitrary user pins.
3. **Break the trip into riding days**, with per-day mileage and a warning when a day exceeds a rider-set limit.
4. **Warn on fuel range.** The GSA has roughly a 300-mile tank, but that is not the constraint — the constraint is that *there is no fuel on the Parkway at all* and some gaps between usable exits exceed 30 miles of Parkway plus a 15-mile detour. Flag any day where the plan puts more than N miles between fuel exits.
5. **Route along the Parkway**, not across country. The Parkway centerline geometry is provided — use it.
6. **Export GPX** that loads into his Garmin and actually follows the Parkway. This is the hard part. See §5.

### Data provenance — read this before you trust anything

- **Campgrounds** came from four parallel research passes plus an adversarial fact-check pass that caught two errors. Every entry was verified to have hot showers and flush toilets. Prices and seasons are 2026 published rates.
- **Fuel** is cross-referenced from two independent published exit lists (blueridgeparkway.org and blueridgeparkwayoverlooks.com, which agree exactly on the Virginia exits) with station coordinates resolved from OpenStreetMap. Each record carries a `confidence` field: `verified`, `likely`, or `unverified`. **Respect it in the UI.** MP 248.1 Laurel Springs is on every official exit list and has no verifiable station — that's exactly the kind of thing that strands a rider.
- **Parkway centerline** is OSM relation 55450, stitched from 551 way segments into a single north-to-south polyline and simplified. Measured length 451.7 mi, scaled to the official 469.1. Milepost positions derived from it are accurate to roughly ±2 miles — good enough to place a pin, not good enough to print on a sign.
- **Closures** are from the NPS page dated **August 16, 2026**. These change. Re-fetch before the trip.

## 4. Architecture

Recommended, but argue with it if you disagree:

- **Keep it a static site.** No backend. It deploys to the existing Vercel project unchanged and works from a phone in a parking lot.
- **Routing: don't run a router.** Snap each stop to the nearest point on the provided Parkway centerline, then slice the centerline between consecutive stops. That *is* the route for the on-Parkway portion — the Parkway has no alternatives between junctions. Only the off-Parkway legs (getting to a campground, running down to a gas station) need real routing, and those can be straight-line hints or a call to a public OSRM instance.
- **Reserve a build step only if you need one.** v1 was generated by a Python script that inlined data into HTML. That's fine and it keeps the deploy trivial. If v2 wants a framework, the Vercel project handles it, but weigh it against the value of a single file that opens offline.
- **Persist trips in localStorage**, and support export/import of a trip as JSON so the group can share plans.

## 5. GPX export — the part that will go wrong

This section is the reason the research was done up front. Read all of it before writing the exporter.

### 5.1 The core problem

**A GPX route is not a path.** It is a list of points plus two hints. The device recomputes which roads connect those points, using *its own* settings. Garmin says so explicitly: "The route will recalculate based on the settings of the zūmo XT during the import process."

Only two routing preferences cross from the file into the device:

- `trp:TransportationMode` (Motorcycling / Automotive)
- `trp:CalculationMode` (FasterTime / ShorterDistance)

Avoidances, curvy-road preference, traffic rerouting — all live on the device and are **not** in the file. So a route that says only "start Asheville, end Boone" will be sent down I-40, correctly, by the device's own logic. Preventing that is the exporter's whole job.

### 5.2 Point types

| Type | GPX encoding | Behavior |
|---|---|---|
| **Via point** | `<rtept>` + `<trp:ViaPoint>` | Announced stop. Orange flag, appears in turn list, has ETA, selectable as re-entry point. Counts against the ~29 limit. |
| **Shaping point** | `<rtept>` + `<trp:ShapingPoint/>` (empty element) | Silent. Pulls the route onto a specific road. No announcement, no ETA. Budget 125. |
| **Waypoint** | `<wpt>` | Saved location in Favorites. Not part of routing. |

**Critical default:** an `<rtept>` with no `trp:` extension is treated as a **via point**. This is why plain GPX from Strava/RideWithGPS blows past the limit and triggers "convert some to non-alerting?" — or worse, silently splits the route into fragments.

### 5.3 Do not use `gpxx:rpt`

Garmin's `gpxx:RoutePointExtension` can carry a list of `<gpxx:rpt>` "ghost points" that reproduce exact geometry without costing points. **They are discarded the moment the device recalculates.** A route built this way looks perfect on import and collapses to straight-lines-between-vias the first time anything triggers a recalc. Some route planners call this "GPX 1.2" — it is not a real GPX version, and it is a trap.

Encode geometry as **shaping points**, which survive recalculation. Garmin's guarantee: "however the route is calculated, it will always pass through every Shaping Point and Via Point."

### 5.4 Point budget — the binding constraint

Different devices cap differently, and he doesn't know which he has. Design to the intersection:

| Limit | Value | Source device |
|---|---|---|
| Via points per route | 29–30 | zūmo XT / 595 / Navigator VI |
| Total route points | **50** | BMW ConnectedRide Navigator |
| Total route points before silent route→track conversion | **62** | Garmin Tread app |
| Shaping points per route | 125 | Garmin FAQ |

**Target: ≤ 50 total `<rtept>`, of which ≤ 25 are via points, ≤ 10,000 `<trkpt>`.** That clears every device with headroom. If a day exceeds it, **split the day into two routes** — do not thin the shaping points.

### 5.5 Shaping point placement for the Parkway

The failure mode isn't gradual drift, it's the router taking an off-ramp at a crossing. So:

> **One shaping point every ~5 miles, PLUS a mandatory shaping point 0.2–0.3 mi *past* every junction where the Parkway meets a US or state highway.**

A point immediately after the junction, on the Parkway, makes the shortcut geometrically impossible. Between junctions the Parkway has no alternatives, so 5-mile spacing is generous insurance.

Budget check: a 130-mile day ≈ 26 spacing points + ~10 junction points + 2 endpoints + 3 named stops ≈ **41 points**. Fits.

Rules:
- Snap every shaping point to the centerline. Off-centerline points snap to parallel service roads.
- Never place one *in* an intersection — put it on the departing leg.
- Never place one on a bridge or overpass (ambiguous snapping).
- Do not lace the route with points every half mile. It isn't more accurate, it multiplies rename bugs, and it destroys the ability to skip ahead after a detour.

### 5.6 Always ship a `<trk>` alongside the `<rte>`

Tracks are immutable — the device cannot recalculate them. Emit the exact intended geometry as a track in a contrasting color. The rider displays both; if the magenta route leaves the blue track, he knows instantly that it recalculated and can follow the track instead. This is the standard workaround across every rider forum, it costs nothing, and it's the thing that saves the morning when the route misbehaves.

### 5.7 File format

GPX **1.1**, UTF-8, no BOM. Required namespaces:

```
xmlns="http://www.topografix.com/GPX/1/1"
xmlns:gpxx="http://www.garmin.com/xmlschemas/GpxExtensions/v3"
xmlns:trp="http://www.garmin.com/xmlschemas/TripExtensions/v1"
```

Set `<trp:TransportationMode>Motorcycling</trp:TransportationMode>` and `<trp:CalculationMode>FasterTime</trp:CalculationMode>`. Not because they help routing, but because an unrecognized value forces a full recalculation.

Include `<gpxx:Subclass>000000000000FFFFFFFFFFFFFFFFFFFFFFFF</gpxx:Subclass>` on each rtept — the null map handle stops the device renaming your points to map-database names.

Emit **one `<rte>` per file, one file per riding day.** Name files and routes ASCII-only, ≤ 30 chars, no punctuation beyond `-` and `_`.

A full annotated example is in `GPX-REFERENCE.md`.

### 5.8 Export variants

Ship three downloads per day:

- **`BRP-D3-Asheville-Boone.gpx`** — route + track + waypoints, the rules above. Works on all four candidate devices.
- **`BRP-D3-Asheville-Boone-track.gpx`** — track + waypoints only, no route. The universal fallback: cannot be recalculated, imports everywhere, convertible to a route on-device.
- **`BRP-D3-Asheville-Boone.kml`** or a plain waypoint file — optional, for anyone in the group on a phone app instead.

## 6. His device — unknown, handle all four

He bought a Garmin as a BMW factory accessory around 2023. Most likely a **BMW Navigator VI** (rebadged zūmo 595) or a **BMW ConnectedRide Navigator**. Possibly a **zūmo XT** or **XT2**.

**Put a device-identification helper in the UI.** The fastest test needs no computer:

- Menus offer **"Trip Planner"** → Garmin firmware (Navigator VI or zūmo XT)
- Menus offer **"Route import"** and mention **anchor points** → ConnectedRide Navigator
- Has **Collections** and pairs with the **Tread** app → zūmo XT2

Transfer paths differ and this matters:

| Device | Where the GPX goes |
|---|---|
| zūmo XT | Internal storage → `GPX` folder. SD card → `\Garmin\GPX\`. Then Trip Planner → Import. |
| zūmo XT2 | Internal or SD → `GPX` folder at root. **Do not use the Tread app** — its cloud sync discards shaping points and silently converts >62-point routes to tracks. |
| Navigator VI | `\Garmin\GPX\`. Prefer the SD card — routes imported from internal storage are destroyed by "Delete route." |
| ConnectedRide Navigator | USB-C → the folder named **`Routes`** (not `GPX`). Then Routes → Options → Route import, and choose **anchor points** for shaping, **waypoints** for named stops. Requires firmware ≥ `20240819-V1.0.4`. Invisible to all Garmin software. |

## 7. Rider-side settings the file cannot control

Surface this checklist next to the download button:

1. Vehicle profile **Motorcycle**, route preference **Faster Time**
2. **All avoidances OFF** — they fight the shaping points
3. **Off-route recalculation OFF** or Prompted
4. Traffic rerouting **OFF**
5. Allow U-turns **ON**
6. Only **one** navigable map enabled
7. Load the track as well as the route, in a contrasting color
8. At "select next destination," always pick the first entry

## 8. Acceptance criteria

The build is done when:

- [ ] A 3-day Asheville→Cherokee trip can be planned in under two minutes on a phone
- [ ] Every exported day is ≤ 50 route points and ≤ 25 via points, enforced not just warned
- [ ] A generated GPX loaded on a real device follows the Parkway end to end with zero interstate miles
- [ ] The planner refuses to route through a closed segment, and offers the signed detour instead
- [ ] Any day with a fuel gap over the rider's threshold is flagged before export
- [ ] `confidence: unverified` fuel stops are visually distinct and cannot be silently relied on
- [ ] The whole thing still opens and works with no network connection

## 9. Known landmines

- **MP 248.1 Laurel Springs** is on every official fuel list and has no verifiable station.
- **MP 344.1 NC 80** is inside a closed segment. Unreachable. It must not appear as a routable stop in 2026.
- **MP 330.9 Spruce Pine** sits in a 6.4-mile orphaned segment closed at both ends — reachable only from NC 226. It's a detour re-entry point, not an en-route stop.
- **MP 393.6 → 443.1** is 49.5 Parkway miles with one exit in the middle that costs 12–18 miles each way. This is the stretch that strands people.
- **MP 317.5 → 382.5** is a 65-mile hole in 2026. Not a ride — a full surface-road detour.
- The Parkway centerline milepost mapping is ±2 miles. Don't present it as exact.
